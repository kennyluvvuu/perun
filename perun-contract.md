# Контракт Perun для плагина 1C:EDT

Документ описывает, что плагин «ПерУН для 1C:EDT» (`com.example.edtai`) ожидает от Perun. Первая часть — то, на что плагин опирается уже сейчас: это нельзя менять без согласования. Вторая — что нужно доработать в Perun, чтобы плагин мог отказаться от обходных решений.

Проверено на Perun 0.1.8 (`develop`, `8386d9b`).

## Как плагин работает с Perun

- Плагин запускает `perun --mode rpc [доп. аргументы]` дочерним процессом. Рабочий каталог — каталог проекта 1С в EDT.
- Общение идёт по протоколу из `RPC_DOCS.md`: JSONL через stdin/stdout, каждая запись — одна строка, разделитель только `\n`. Ответы сопоставляются с командами по `id`, stderr считается журналом.
- Сессия хранится на диске: флаг `--no-session` не используется.
- Плагин завершает Perun закрытием stdin. Если процесс не вышел за 2 секунды, плагин его убивает.

## Часть 1. На что плагин опирается сейчас (не ломать)

### 1.1. Запуск и окружение

| Что | Требование |
|---|---|
| Команда | `perun --mode rpc` работает без интерактивных вопросов и сразу принимает команды |
| `--version` | Печатает версию и завершается |
| `PERUN_CODING_AGENT_DIR` | Переопределяет каталог настроек агента (по умолчанию `~/.perun/agent`) |
| `APP_NAME=perun` | Каталог настроек `.perun`, имя `perun` |
| stdout | Только протокольные JSON-строки, никакого текста. Цветные ANSI-коды в полях тоже нежелательны (см. 2.2) |

### 1.2. Команды

| Команда | Что берёт плагин из ответа |
|---|---|
| `prompt` (`message`, всегда с `streamingBehavior: "followUp"`) | `data.disposition`: `started` / `queued` / `handled`; при ошибке preflight — `success:false` и `error` (например, «No API key found») |
| `abort` | только `success` |
| `get_state` | `model` (`id`, `name`, `provider`, `reasoning`), `thinkingLevel`, `isStreaming`, `sessionFile`, `sessionName` |
| `get_available_models` | `models[]` с теми же полями |
| `get_available_thinking_levels` | `levels[]`: `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` |
| `set_model` (`provider`, `modelId`) | только `success` |
| `set_thinking_level` (`level`) | только `success` |
| `get_messages` | `messages[]`: `role` (`user` / `assistant` / `toolResult`), `content` (строка или блоки `text` / `thinking` / `toolCall`), `toolCallId`, `isError`, `timestamp` |
| `new_session` | только `success` |
| `switch_session` (`sessionPath`) | только `success` |
| `get_commands` | `commands[]`: `name`, `description`, `source` (`extension` / `skill` / `prompt`) |
| `compact` (`customInstructions`) | `tokensBefore`, `estimatedTokensAfter`, текст ошибки |
| `set_session_name` (`name`) | только `success` |
| `export_html` | `path` (сейчас относительный к рабочему каталогу) |
| `get_session_stats` | `userMessages`, `assistantMessages`, `toolCalls`, `tokens.total`, `cost`, `contextUsage.percent` |
| `submit_feedback` (`feedback`) | `received: true`; отзыв сохраняется в постоянную память SQLite (`~/.perun/agent/memory.db`) |

### 1.3. События

| Событие | Поля, которые читает плагин |
|---|---|
| `message_start` | `message.role` (берутся только `assistant`) |
| `message_update` | `assistantMessageEvent.type` (`text_delta`, `thinking_delta`), `contentIndex`, `delta` |
| `message_end` | `message.content[]`, `message.stopReason`, `message.errorMessage` |
| `tool_execution_start` | `toolCallId`, `toolName`, `args` |
| `tool_execution_end` | `toolCallId`, `isError`, `result.content[]` (текст) |
| `agent_settled` | `aborted`; по нему плагин считает ответ законченным |
| `auto_retry_start` | `attempt`, `maxAttempts` |
| `compaction_start` | факт события |
| `extension_error` | `error` |

### 1.4. Запросы к интерфейсу (`extension_ui_request`)

| `method` | Как использует плагин |
|---|---|
| `confirm` | Карточка «Разрешить / Отклонить». Имя инструмента плагин вырезает из `title` по шаблону `'<имя>'`. На этом построены правила «в этой сессии / всегда / никогда» |
| `select`, `input`, `editor` | Карточки с вариантами или полем ввода; ответ через `extension_ui_response` (`value` / `confirmed` / `cancelled`) |
| `notify` | Всплывающее уведомление. Многострочный текст или текст длиннее 180 символов показывается карточкой в чате |
| `setStatus` | Ключи `1c-mode` (текст `[1C: НАЙТИ / ОБЪЯСНИТЬ / НАПИСАТЬ / ПЛАНИРОВАТЬ]`) и `1c-permissions`. Режим плагин распознаёт по этим словам |
| `set_editor_text` | Подставляет текст в поле ввода |

### 1.5. Слэш-команды

- `/mode find|explain|write|plan` выполняется через `prompt` и возвращает `handled`. Плагин переключает режим этой командой и ждёт `setStatus` с ключом `1c-mode`.
- Остальные команды из `get_commands` плагин показывает в списке и отправляет как есть.
- Встроенные команды TUI (`/login`, `/new`, `/model`, `/compact` и т.д.) в RPC не работают, поэтому плагин реализует их сам через команды из 1.2.

### 1.6. Инструменты записи файлов

По ним плагин размечает код, написанный агентом.

| Инструмент | Аргументы, которые читает плагин |
|---|---|
| `edit` | `path` (абсолютный или от рабочего каталога), `edits[]` с `oldText` и `newText` |
| `write` | `path`, `content` |

В `tool_execution_end.result.details.ranges` передаются 1-based диапазоны строк изменённых блоков в новом файле: `Array<{ startLine: number, endLine: number }>`. Для `write` возвращается `ranges: [{ startLine: 1, endLine: lineCount }]`. Плагин может опираться на эти диапазоны напрямую, без самостоятельного поиска текста.

### 1.7. Файлы на диске

| Файл | Зачем плагину |
|---|---|
| `<agentDir>/sessions/<закодированный cwd>/*.jsonl` | Список истории чатов: заголовок `session`, записи `session_info.name` и первое сообщение пользователя |
| `<agentDir>/auth.json` | Команда `/login` в плагине пишет `{"<провайдер>": {"type": "api_key", "key": "…"}}` с правами 600 и перезапускает Perun |

Каталог `agentDir` плагин вычисляет из `get_state.sessionFile` (три уровня вверх). Если путь пустой, берётся `PERUN_CODING_AGENT_DIR`, а если и его нет — `~/.perun/agent`.

### 1.8. Что плагин добавляет в текст промпта

Это не часть протокола, но Perun должен воспринимать эти блоки как обычный текст пользователя. Блоки сохраняются в истории, а при показе плагин их скрывает.

- `<project-rules>…</project-rules>` — правила проекта из каталога `.perun/rules/*.md`;
- `<context file="…" lines="a-b">…</context>` — выделенный код или открытый файл.

## Часть 2. Что доработать в Perun

Пункты отсортированы по важности для плагина.

### 2.1. Поставка и сборка — обязательно

1. **Собранные артефакты.** Каталог `packages/1c-agent/bin` убран из репозитория, а бинарник собирается только под macOS. Нужны готовые сборки как минимум для `linux-x64` и `win-x64`: Node-бандл со всеми зависимостями (сейчас без отдельно установленного `jiti` он не запускается) или работающий нативный бинарник. Хорошо бы выкладывать их в GitHub Releases с номером версии.
2. **Нативный бинарник на Linux падает при старте:** `TypeError: webidl.util.markAsUncloneable is not a function` в `undici` под bun 1.3.11. Нужно закрепить совместимую версию `undici` или bun либо исключить `undici` из сборки.
3. **`scripts/build-perun.mjs` падает с `ENOENT`, если нет папки `packages/1c-agent/bin`.** Скрипт должен создавать её сам. *(Реализовано: `scripts/build-perun.mjs` создаёт папку автоматически перед записью бандла).*
4. **`package-lock.json` должен совпадать с версиями пакетов.** В 0.1.3 `npm ci` отказывался работать, и приходилось ставить через `npm install`.
5. **Node-бандл ищет шаблоны в `dist/core/export-html` и `dist/modes/interactive/theme`,** а сборка кладёт их в `bin/export-html` и `bin/theme`. Без ручных ссылок `/export` падает. Пути поиска и раскладка сборки должны совпадать.

### 2.2. Чистые данные в статусах и запросах — важно

1. **`setStatus.statusText` приходит с ANSI-кодами цвета** (`\u001b[38;5;5m…`). Нужен простой текст, а лучше машинно читаемое значение отдельным полем, например `statusValue: "write"` для `1c-mode` и `"auto-approve"` для `1c-permissions`.
2. **`confirm` должен содержать структурированные поля, а не только заголовок для человека.** Нужны `toolName`, `args` (для bash — сама команда, для `edit` — путь) и `reason`. Сейчас плагин вырезает имя инструмента из `title` регулярным выражением и не видит, что именно будет выполнено.
3. **Если на `confirm` первым ответил Telegram-бот, RPC-клиенту об этом не сообщается** (п. 2 нюансов в `perun-integration.md`). У плагина карточка повиснет навсегда. Нужно событие `extension_ui_request` с `method: "dismiss"` и тем же `id`, чтобы плагин мог её закрыть.

### 2.3. Команды вместо обходных путей — важно

| Нужна команда | Зачем | Что сейчас делает плагин |
|---|---|---|
| `list_sessions` (`cwd` по желанию) → `path`, `name`, `firstMessage`, `modified`, `messageCount` | История чатов | Читает `.jsonl` из каталога сессий |
| `set_api_key` (`provider`, `key`), `remove_api_key`, `list_providers` (с признаком `configured`) | Команда `/login` | Пишет `auth.json` сам и перезапускает процесс |
| Перечитать модели и ключи без перезапуска (событие или команда `reload_auth`) | Подключить ключ без перезапуска | Перезапускает Perun |
| `get_mode` и `set_mode` с ответом `mode` | Режим без слэш-команды и разбора текста статуса | Шлёт `/mode …` и ждёт `setStatus` |
| `get_permission_policy` и `set_permission_policy` | Показывать и менять политику прав | Не умеет |
| `export_html` с абсолютным `path` в ответе | Показать, куда сохранён файл | Склеивает путь с рабочим каталогом |

### 2.4. Разметка кода, написанного агентом, — важно

Плагин подсвечивает код ИИ в редакторе и собирает отзывы на него. Сейчас он угадывает место правки поиском текста. Нужно:

1. **В `tool_execution_end` для `edit` и `write` передавать в `result.details` итоговые диапазоны изменений:** путь к файлу, начальная и конечная строка (или смещения в символах) для каждого изменённого блока в файле после записи. Тогда разметка будет точной даже при повторяющемся тексте. *(Реализовано: в `result.details.ranges` передаются 1-based диапазоны строк `Array<{ startLine: number, endLine: number }>`)*.
2. **Не менять имена `edit` / `write` и схему их аргументов без согласования.** Если появится новый инструмент записи (например, `bsl_fix_standards` или навыки, которые правят файлы), он должен отдавать такие же `details` с диапазонами.
3. **В `message_end` у ассистента передавать `responseId` или другой стабильный идентификатор ответа.** По нему плагин свяжет отзыв в чате с кодом, вставленным из этого ответа.

### 2.5. Контекст и правила — желательно

1. **Прикреплённый код** — опциональное поле `attachments[]` у команды `prompt`: `path`, `startLine`, `endLine`, `text`. Сейчас плагин дописывает блок `<context>` в текст сообщения, и этот блок попадает в историю.
2. **Правила проекта** Perun может читать сам из `.perun/rules/*.md` (формат описан в README плагина, раздел «Где хранятся отзывы и правила») с учётом области (`module` / `folder` / `config`). Тогда правила будут действовать и в TUI, и в Telegram, а не только в плагине. Если Perun возьмёт это на себя, плагин перестанет добавлять блок `<project-rules>`. Это нужно согласовать, чтобы правила не добавлялись дважды.
3. **В `get_messages` отдавать текст пользователя без служебных блоков** или отдельным полем, чтобы плагину не приходилось их вырезать.

### 2.6. Отзывы — желательно

Хранение и разбор отзывов в `.md` делает отдельная часть системы. Формат файлов, которые пишет плагин, описан в README плагина. От Perun нужно:

- если агент сам читает каталог `.perun/feedback`, не менять формат файлов без согласования;
- по желанию — команду `submit_feedback` с полями файла отзыва, чтобы плагин мог передавать отзыв через RPC, а не только файлом. *(Реализовано: поддержана RPC-команда `submit_feedback`, сохраняющая отзывы и правила в SQLite-память `~/.perun/agent/memory.db` и передающая их расширениям через событие `submit_feedback`).*

### 2.7. Версия протокола — желательно

- В ответе `get_state` нужно поле `rpcVersion` (целое число), которое увеличивается при несовместимых изменениях протокола. Плагин будет сверять его при запуске и показывать понятную ошибку вместо тихой поломки.
- В `CHANGELOG` нужно отмечать изменения команд, событий и аргументов инструментов из этого документа.

## Как проверить

Для каждой доработки из части 2 достаточно RPC-сценария через stdin/stdout, без EDT:

1. **Сборка.** На чистом Linux `perun --version` и `perun --mode rpc` с `get_state` работают из выложенной сборки без `npm install`.
2. **Статусы.** После `/mode write` приходит `setStatus` без ANSI-кодов и с `statusValue: "write"`.
3. **Подтверждения.** В режиме `strict` `confirm` для `bash` содержит `toolName: "bash"` и команду в `args`. Если ответил Telegram-бот, клиент получает `dismiss`.
4. **Разметка.** После `edit` в `tool_execution_end.result.details` есть диапазоны, и по ним в файле лежит ровно новый текст.
5. **Ключи.** `set_api_key` → `get_available_models` сразу возвращает модели провайдера, без перезапуска.
6. **История.** `list_sessions` возвращает те же сессии, что лежат в каталоге сессий.
