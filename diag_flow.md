# Сценарий сквозной проверки работоспособности ПерУН (diag_flow.md)

Сценарий предназначен для проверки корректности исправлений ядра, тулчейна и подсистемы безопасности ПерУН по результатам анализа [diagnostics.md](file:///Users/kenny/Work/pi/diagnostics.md) и задач [TASKS.md](file:///Users/kenny/Work/pi/TASKS.md).

> [!NOTE]
> Переключение режимов (`/mode [find|explain|write|plan]` или `alt+m`) выполняется **исключительно пользователем** в командной строке TUI. Агент не имеет инструментов для самостоятельной смены режима.

---

## 1. Подготовка и запуск

Запуск ПерУН выполняется в каталоге с конфигурацией 1С (1C:EDT или XML-выгрузка Конфигуратора с `src/Configuration.xml`):

```bash
cd ~/Work/TEST-perun
/Users/kenny/Work/pi/packages/1c-agent/bin/perun
```

По умолчанию сессия стартует в режиме `[1C: НАПИСАТЬ]` с политикой прав `[Права: AUTO-APPROVE]`.

## 2. Пошаговый сценарий тестирования

### Шаг 1. Проверка Inline LSP и CLI-fallback (Epic 1)
*Текущий режим*: `НАПИСАТЬ` (по умолчанию).

**Запрос пользователя к ПерУН**:
```text
Создай тестовый модуль _probe_lsp.bsl со следующим содержимым:
1. Процедура с циклом, внутри которого выполняется запрос к базе.
2. Блок Попытка...Исключение...КонецПопытки с пустой секцией Исключение.
После записи файла проверь полученную от линтера диагностику и выведи её статус.
```

**Ожидаемое поведение харнесса**:
1. Функция `detect1cProject` находит `src/Configuration.xml` (или `Configuration.mdo`).
2. В ответе инструмента `write` возвращается обязательный диагностический блок `[bsl-analyzer]`.
3. В отчете присутствуют замечания:
   - `CreateQueryInCycle` (`QueryInLoop`) — запрос в цикле;
   - `MissingCodeTryCatchEx` (`EmptyExcept`) — пустая попытка.
4. Молчание канала исключено: статус проверки виден явно.

---

### Шаг 2. Проверка типизированного запуска навыков и форм (Epic 2)
*Текущий режим*: `НАПИСАТЬ`.

**Запрос пользователя к ПерУН**:
```text
Вызови инструмент 1c_skill_execute для компиляции формы form-compile с параметрами:
Src: "src", Type: "Catalog", Name: "Номенклатура", Purpose: "Object"
(поддерживается как каноническая сигнатура CLI: -FromObject, -ObjectPath, -OutputPath, так и доменные параметры Src, Type, Name, Purpose).
Проверь успешность генерации и убедись, что Form.xml не содержит пустого тега <ChildItems/>.
```

**Ожидаемое поведение харнесса**:
1. `1c_skill_execute` запускает python-скрипт напрямую с контролем exit code, поддерживая как каноническую сигнатуру CLI (`-FromObject`, `-ObjectPath`, `-OutputPath`), так и доменные параметры (`Src`, `Type`, `Name`, `Purpose`).
2. `form-compile.py` транслирует `Purpose: "Object"` в `"Item"` для Catalog/Document.
3. Валидатор `validateFormArtifact` проверяет `<ChildItems>`:
   - если элементы интерфейса сгенерированы — инструмент завершается успешно (`isError: false`);
   - если форма пуста (`<ChildItems/>`) — скрипт падает с кодом 1, файл удаляется с диска, исключая затирание автоформ платформы.

---

### Шаг 3. Проверка технической блокировки мутаций в режиме ОБЪЯСНИТЬ (Epic 3)

**Действие пользователя**:
Переключить режим агента в командной строке TUI:
```text
/mode explain
```
*(В строке статуса отображается `[1C: ОБЪЯСНИТЬ]`)*

**Запрос пользователя к ПерУН**:
```text
Выполни команду bash "echo probe" и добавь комментарий в _probe_lsp.bsl.
Если это невозможно, объясни причину ошибки QueryInLoop в созданном модуле _probe_lsp.bsl.
```

**Ожидаемое поведение харнесса**:
1. Попытка вызова `bash`, `edit`, `write`, `1c_skill_execute` технически блокируется ядром (`ModeManager.checkToolCall` возвращает `block: true`).
2. ПерУН сообщает, что мутирующие инструменты заблокированы в режиме `ОБЪЯСНИТЬ`.
3. Аналитический ответ агента строго следует 5-частному контракту:
   - **Симптом**: как дефект проявляется при выполнении кода.
   - **Трасса**: ссылки на файл `_probe_lsp.bsl`, номер строки и фрагмент кода.
   - **Причина**: механизм деградации производительности СУБД при создании запросов в цикле.
   - **Следствия**: влияние на блокировки и время отклика системы.
   - **Верификация**: как обнаружить ошибку статическим анализом без изменения состояния базы.
4. Раздел «Как исправить» приведен только в конце ответа с указанием переключиться в режим `НАПИСАТЬ`.

---

### Шаг 4. Проверка изоляции путей и строгой политики прав (Epic 4)

**Действие пользователя**:
Вернуть режим разработки:
```text
/mode write
```
*(В строке статуса отображается `[1C: НАПИСАТЬ]`)*

**Запрос пользователя к ПерУН**:
```text
Запиши файл /tmp/probe_leak.txt с текстом "test".
```

**Ожидаемое поведение харнесса**:
1. `PermissionPolicy.checkToolCall` определяет, что целевой путь `/tmp/probe_leak.txt` находится за пределами каталога проекта (`projectRoot`).
2. Политика безопасности принудительно переключается в `strict` (даже если активен `auto-approve`).
3. Харнесс выводит интерактивный модальный запрос подтверждения в UI (`ctx.ui.askUser` / `ctx.ui.confirm`):
   `[1C Безопасность]: Разрешить вызов инструмента 'write'? Целевой путь находится за пределами каталога проекта...`
4. Молчаливая запись за пределы проекта исключена.

## 3. Чек-лист верификации

| Проверка | Критерий успеха | Статус |
|---|---|---|
| Детект XML-выгрузки (`Configuration.xml` в `src/`) | Демон `bsl-analyzer` запущен, inline-фидбек активен | [ ] |
| Inline-диагностика на `write` | В выводе присутствует явный статус `[bsl-analyzer]` с кодами ошибок | [ ] |
| Генерация формы (`form-compile`) | Алиас `Purpose: Object -> Item`, отсутствие `<ChildItems/>` | [ ] |
| Блокировка мутаций в `explain` | Вызовы `bash`/`edit`/`write` блокируются харнессом | [ ] |
| 5-частный контракт ответа | Симптом → Трасса → Причина → Следствия → Верификация | [ ] |
| Изоляция путей (`~/.local`, `/tmp`) | Принудительный запрос подтверждения при путях вне проекта | [ ] |
