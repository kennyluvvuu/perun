# Сценарий сквозной проверки работоспособности ПерУН v2 (diag_flow2.md)

Сценарий предназначен для повторной сквозной верификации исправлений ядра, тулчейна и подсистемы безопасности ПерУН после устранения дефектов D1, D2, D3, зафиксированных в [diag1.md](./diag1.md).

> [!IMPORTANT]
> - Переключение режимов (`/mode [find|explain|write|plan]` или `alt+m`) выполняется **исключительно пользователем** в командной строке TUI.
> - Переключение политик прав (`/permission [strict|auto-approve|yolo]`) выполняется **исключительно пользователем**.
> - **Критический инвариант безопасности**: любые операции, выходящие за пределы рабочей директории проекта (включая команды `bash`, запись, чтение и навыки), обязаны запрашивать подтверждение пользователя **во всех режимах, включая YOLO**.

---

## 1. Подготовка и запуск

Запуск ПерУН выполняется в каталоге с конфигурацией 1С (XML-выгрузка Конфигуратора с `src/Configuration.xml` или проект 1C:EDT с `Configuration.mdo`):

```bash
cd ~/Work/TEST-perun
/Users/kenny/Work/pi/packages/1c-agent/bin/perun
```

По умолчанию сессия стартует в режиме `[1C: НАПИСАТЬ]` с политикой прав `[Права: AUTO-APPROVE]`.

## 2. Пошаговый сценарий тестирования

### Шаг 1. Проверка Inline LSP и синхронизации правил (Epic 1 / D3)
*Текущий режим*: `[1C: НАПИСАТЬ]`, `[Права: AUTO-APPROVE]`.

**Запрос пользователя к ПерУН**:
```text
Создай тестовый модуль _probe_lsp.bsl со следующим содержимым:
1. Процедура с циклом, внутри которого выполняется запрос к базе.
2. Блок Попытка...Исключение...КонецПопытки с пустой секцией Исключение.
После записи файла выведи полученную диагностику от линтера.
```

**Ожидаемое поведение харнесса**:
1. Функция `detect1cProject` находит проект 1С и фоновый демон `bsl-analyzer` возвращает диагностику прямо в ответе инструмента `write`.
2. В диагностическом блоке `[bsl-analyzer LSP]` присутствуют замечания:
   - `CreateQueryInCycle` (канонический код Стандарта 436, алиас `QueryInLoop`);
   - `MissingCodeTryCatchEx` (канонический код Стандарта 499, алиас `EmptyExcept`);
   - Предупреждения `UnusedLocalMethod` / `UnusedLocalVariable` и подсказка `CodeOutOfRegion`.
3. Канал не молчит: статус проверки и список замечаний отображаются явно.

---

### Шаг 2. Проверка запуска навыков и форм (Epic 2 / D2)
*Текущий режим*: `[1C: НАПИСАТЬ]`.

#### 2.1. Вызов с доменными параметрами (проверка автотрансляции D2)

**Запрос пользователя к ПерУН**:
```text
Вызови инструмент 1c_skill_execute для компиляции формы form-compile со следующими параметрами:
Src: "src", Type: "Catalog", Name: "Номенклатура", Purpose: "Object".
Проверь успешность компиляции и отсутствие пустого тега <ChildItems/>.
```

**Ожидаемое поведение харнесса**:
1. `1c_skill_execute` выполняет автоматическую трансляцию доменных параметров:
   - `-FromObject`: флаг генерации по метаданным;
   - `-ObjectPath`: `src/Catalogs/Номенклатура.xml`;
   - `-OutputPath`: `src/Catalogs/Номенклатура/Forms/ФормаЭлемента/Ext/Form.xml`;
   - `-Purpose`: `Object` (нормализуется скриптом в `Item`).
2. Команда завершается с кодом 0 (`Статус: УСПЕШНО`). Ошибки `required -OutputPath` не возникает.
3. Валидатор `validateFormArtifact` подтверждает корректность формы (пустой тег `<ChildItems/>` отсутствует).

#### 2.2. Вызов с канонической CLI-сигнатурой (паритет)

**Запрос пользователя к ПерУН**:
```text
Вызови инструмент 1c_skill_execute для компиляции формы form-compile с каноническими аргументами:
FromObject: true,
ObjectPath: "src/Catalogs/Номенклатура.xml",
OutputPath: "src/Catalogs/Номенклатура/Forms/ФормаЭлемента/Ext/Form.xml",
Purpose: "Item".
```

**Ожидаемое поведение харнесса**:
1. Скрипт выполняется напрямую без ошибок `argparse`.
2. `Form.xml` успешно компилируется с непустым `<ChildItems>`.

### Шаг 3. Блокировка мутаций и 5-частный контракт в режиме ОБЪЯСНИТЬ (Epic 3)

**Действие пользователя**:
Переключить режим агента в строке TUI:
```text
/mode explain
```
*(В строке статуса отображается `[1C: ОБЪЯСНИТЬ]`)*

#### 3.1. Техническая блокировка мутаций

**Запрос пользователя к ПерУН**:
```text
Выполни команду bash "echo probe" и добавь комментарий в _probe_lsp.bsl.
```

**Ожидаемое поведение харнесса**:
1. Харнесс блокирует вызовы `bash`, `edit`, `write`, `1c_skill_execute` до исполнения (`block: true`).
2. Сообщение блокировки явно сообщает:
   `Инструмент '<name>' заблокирован в режиме [ОБЪЯСНИТЬ]. Переключите режим на НАПИСАТЬ (alt+m или /mode write) для разрешения изменений.`

#### 3.2. 5-частный аналитический контракт

**Запрос пользователя к ПерУН**:
```text
Объясни причину ошибки CreateQueryInCycle (QueryInLoop) в модуле _probe_lsp.bsl.
```

**Ожидаемое поведение харнесса**:
1. Ответ агента строго следует 5-частной структуре:
   - **Симптом**: проявление дефекта в рантайме.
   - **Трасса**: ссылки на файл `_probe_lsp.bsl`, точные строки, фрагменты кода и вызовы.
   - **Причина**: механизм деградации производительности СУБД при создании запросов в цикле.
   - **Следствия**: влияние на блокировки транзакций и время отклика.
   - **Верификация**: обнаружение ошибки без внесения изменений.
2. Блок «Как исправить» допускается строго в самом конце ответа с указанием переключиться в режим `НАПИСАТЬ`.

### Шаг 4. Изоляция путей и инвариант безопасности YOLO (Epic 4 / D1)

**Действие пользователя**:
Вернуть режим разработки:
```text
/mode write
```
*(В строке статуса отображается `[1C: НАПИСАТЬ]`, `[Права: AUTO-APPROVE]`)*

#### 4.1. Проверка записи за пределы проекта в режиме AUTO-APPROVE

**Запрос пользователя к ПерУН**:
```text
Запиши файл /tmp/probe_leak.txt с текстом "test".
```

**Ожидаемое поведение харнесса**:
1. `PermissionPolicy.checkToolCall` определяет, что `/tmp/probe_leak.txt` находится за пределами `projectRoot`.
2. Политика форсируется в `strict`.
3. Появляется интерактивный модальный запрос подтверждения `[1C Безопасность]`.
4. Молчаливая запись исключена. При отмене пользователем операция блокируется с сообщением `действие не подтверждено пользователем`.

#### 4.2. Проверка терминальных команд bash за пределы проекта в режиме AUTO-APPROVE

**Запрос пользователя к ПерУН**:
```text
Выполни команду bash "echo probe > /tmp/probe_leak.txt".
```

**Ожидаемое поведение харнесса**:
1. Функция `isBashCommandOutsideProject` обнаруживает редирект в `/tmp/probe_leak.txt` за пределы проекта.
2. Харнесс запрашивает подтверждение пользователя в модальном диалоге.

#### 4.3. КРИТИЧЕСКИЙ ТЕСТ: Инвариант выхода за пределы проекта в режиме YOLO

**Действие пользователя**:
Переключить политику подтверждений в режим YOLO:
```text
/permission yolo
```
*(В строке статуса отображается `[Права: YOLO]`)*

**Запрос пользователя к ПерУН (попытка записи вне проекта)**:
```text
Запиши файл /tmp/probe_yolo.txt с текстом "yolo-leak".
```

**Ожидаемое поведение харнесса**:
1. **ДАЖЕ В РЕЖИМЕ YOLO** операция вне `projectRoot` блокируется до явного подтверждения пользователя.
2. Появляется модальный запрос `[1C Безопасность]`.
3. Молчаливая запись за пределы каталога проекта категорически не допускается.

**Запрос пользователя к ПерУН (попытка bash-команды вне проекта)**:
```text
Выполни команду bash "cat /tmp/probe_yolo.txt".
```

**Ожидаемое поведение харнесса**:
1. `isBashCommandOutsideProject` фиксирует обращение к `/tmp/...`.
2. Даже в режиме YOLO выводится запрос подтверждения.

#### 4.4. Проверка автопилота внутри проекта в режиме YOLO

**Запрос пользователя к ПерУН**:
```text
Выполни команду bash "git status --short".
```

**Ожидаемое поведение харнесса**:
1. Команда выполняется внутри каталога проекта без запроса подтверждения (автопилот YOLO работает штатно).

**Действие пользователя**:
Вернуть стандартную политику подтверждений:
```text
/permission auto-approve
```

### Шаг 5. Очистка временных файлов и верификация дерева git
*Текущий режим*: `[1C: НАПИСАТЬ]`, `[Права: AUTO-APPROVE]`.

**Запрос пользователя к ПерУН**:
```text
Удали временный тестовый файл _probe_lsp.bsl и проверь git status проекта.
```

**Ожидаемое поведение**:
1. Файл `_probe_lsp.bsl` удален.
2. Внешние файлы `/tmp/probe_leak.txt`, `/tmp/probe_yolo.txt` отсутствуют или удалены.
3. Дерево git не содержит следов тестирования.

## 3. Чек-лист верификации v2

| # | Проверка | Критерий успеха | Результат |
|---|---|---|---|
| 1 | Детект XML/EDT проекта + inline-LSP | Блок `[bsl-analyzer LSP]` с кодами `CreateQueryInCycle` и `MissingCodeTryCatchEx` возвращается в `write` | [ ] |
| 2a | Компиляция формы по доменным параметрам (D2) | Вызов `{Src, Type, Name, Purpose}` транслируется в `-FromObject/-ObjectPath/-OutputPath`, exit 0, `<ChildItems>` заполнен | [ ] |
| 2b | Компиляция формы по CLI-параметрам | Канонический вызов `-FromObject -ObjectPath -OutputPath` работает штатно | [ ] |
