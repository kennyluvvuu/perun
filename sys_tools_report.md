## 3. Почему так вышло

1. В системном промпте перечислены навыки, но **нет маппинга «задача → навык»** для чтения артефактов:
   не сказано, что структуру метаданных/формы/СКД/макета нужно получать через `meta-info` / `form-info` / `skd-info` / `mxl-info`,
   а не парсить XML самостоятельно.
2. Нет прямого запрета на ручной парсинг XML/СКД скриптами в `bash` при наличии навыка.
3. Правило про изоляцию путей сформулировано как перечень запрещённых команд (`which`, `find`, `whereis`),
   но не как «внешние бинарники не вызывать вообще — работать только через tool/навык», поэтому триггер не сработал
   и попытка `bash` с абсолютным путём анализатора дошла до политики прав.
4. Нет фиксации «чем проверять результат»: для СКД правильный замкнутый цикл — `skd-validate` после правки,
   для BSL — `bsl_fix_standards`/inline-LSP; без этого правила проверка делается чтением глазами.

## 4. Предложения по обвязке и промпту

1. Добавить в промпт таблицу «артефакт → навык»: `.mdo`/`*.xml` метаданных → `meta-info`, `Form.xml` → `form-info`,
   `Template.xml` СКД → `skd-info`, MXL → `mxl-info`, роли → `role-info`, подсистемы → `subsystem-info`.
2. Добавить правило-запрет: «не парсить XML/СКД скриптами в `bash`, если для этого типа артефакта есть навык».
3. Переформулировать запрет на внешние вызовы: «любой бинарник/скрипт вне каталога проекта вызывается только через
   tool или навык; `bash` — только для операций внутри проекта».
4. Зафиксировать обязательные пост-проверки: правка BSL → inline-LSP или `bsl_fix_standards`; правка СКД → `skd-validate`;
   правка метаданных → `meta-validate`; изменение конфигурации → `1c_vanessa load` + `updatedb`.
5. Для `bsl_fix_standards` поддержать `target = <каталог>` (сейчас `EISDIR`) — иначе пакетный прогон невозможен.
