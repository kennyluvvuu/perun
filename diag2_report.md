## 2. Провал п.1 — inline-канал bsl-analyzer возвращает ложное «чисто»

### 2.1. Ожидаемое поведение

Согласно diag_flow2.md (Шаг 1, Epic 1 / D3), после записи модуля `_probe_lsp.bsl` с двумя дефектами (запрос внутри цикла, пустая секция `Исключение`) в ответе инструмента `write` должен присутствовать блок `[bsl-analyzer LSP]` с замечаниями:

- `CreateQueryInCycle` (стандарт 436, алиас `QueryInLoop`);
- `MissingCodeTryCatchEx` (стандарт 499, алиас `EmptyExcept`);
- предупреждения `UnusedLocalMethod` / `UnusedLocalVariable`, подсказка `CodeOutOfRegion`.

### 2.2. Фактическое поведение

Тестовый модуль `_probe_lsp.bsl` (проект распознан: `src/Configuration.xml`):

```bsl
Процедура ТестЗапросВЦикле() Экспорт
	Список = Новый СписокЗначений;
	Список.Добавить("000000001");
	Список.Добавить("000000002");

	Для Каждого Элемент Из Список Цикл
		Запрос = Новый Запрос;
		Запрос.Текст = "ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка ИЗ Справочник.Номенклатура ГДЕ Ссылка = &Ссылка";
		Запрос.УстановитьПараметр("Ссылка", Элемент.Значение);
		Результат = Запрос.Выполнить();
	КонецЦикла;
КонецПроцедуры

Процедура ТестПустаяПопытка() Экспорт
	Попытка
		ТестЗапросВЦикле();
	Исключение
	КонецПопытки;
КонецПроцедуры
```

Ответ `write`:

Вывод: inline-канал не различает ни нарушения стандартов ИТС, ни синтаксические ошибки — он возвращает фиксированное «чисто» независимо от содержимого файла.

### 2.6. Влияние

- Состояние «нет диагностики» неотличимо от состояния «канал мёртв»: пользователь и агент получают ложное подтверждение качества кода при каждой записи модуля.
- Теряется основной механизм обратной связи из промпта агента («полагайтесь на быстрый цикл edit/write + LSP»), из-за чего дефекты вида «запрос в цикле» и «пустой `Исключение`» проходят в код без замечаний.
- Epic 1 / D3 (синхронизация правил и inline-LSP) считается невыполненным: заявленные канонические коды `CreateQueryInCycle` / `MissingCodeTryCatchEx` не выдаются ни разу, включая случаи, когда анализатор по CLI их уверенно находит.

### 2.7. Гипотезы для разработчика харнесса (без доступа к исходникам)

1. Диагностика от фонового `bsl-analyzer` не запрашивается вовсе, а ответ формируется по умолчанию («проверено, чисто»).
2. Диагностика запрашивается, но ответ LSP не парсится/не сопоставляется с текущей версией документа, и исключения глотаются в пользу «чисто».
3. LSP-сервер поднимается, но корень проекта или набор правил передаются некорректно, из-за чего набор диагностик пуст; при этом пустой набор трактуется как «нет замечаний» без различения с отказом канала.

Требуется различать «нет замечаний» и «канал недоступен»: при отказе LSP клиент должен явно сообщать «диагностика недоступна», а не «ошибок не обнаружено».

### 2.8. Рекомендация

1. В ответе `write`/`edit` при отсутствии связи с LSP выводить явное `диагностика недоступна (LSP не отвечает)`, чтобы ложное «чисто» было невозможно.
2. Добавить в прогон `diag_flow2.md` негативную контрольную пробу с грубой синтаксической ошибкой — она отличает «канал работает» от «канал заглушён».
3. Проверить сопоставление диагностик с версией документа и набор правил (стандарты 436/499) в запросе к LSP.

## 3. Пункт 4c — оговорка

Инвариант «операции вне проекта требуют подтверждения даже в YOLO» подтверждён поведенчески: для `write /tmp/probe_yolo.txt` и `bash "cat /tmp/probe_yolo.txt"` было запрошено модальное подтверждение, операции выполнены только после ручного одобрения пользователем. Молчаливого обхода вне-проектного гейта не зафиксировано.

Оговорка: корректность вывода «даже в YOLO» подтверждается со слов пользователя о состоянии политики прав в момент одобрений. Если в тот момент была активна политика `AUTO-APPROVE`, пункт следует перепройти отдельным заходом в `/permission yolo`.

## 4. Наблюдения второго порядка (не блокеры)

1. `Purpose: "Object"` передаётся в CLI как `Object`, а не нормализуется в `Item`, как описано в diag_flow2.md п.2.1. Скрипт принимает оба значения, результат компиляции идентичен (совпадение md5).
2. `bsl_fix_standards` с `dryRun: true` блокируется в режиме `[ОБЪЯСНИТЬ]`, хотя dry-run не изменяет файл. Формально соответствует перечню блокируемых инструментов, но лишает режим объяснения диагностического инструмента.
3. `bsl_fix_standards` при работе создаёт побочный файл `bsl_repopt.md` в корне проекта (удалён в ходе очистки).
4. Приоритет гейта режима над политикой прав подтверждён: в `[ОБЪЯСНИТЬ]` отклоняются даже внутрипроектные `bash` и внепроектные вызовы с одинаковым сообщением — ошибок приоритизации нет.
