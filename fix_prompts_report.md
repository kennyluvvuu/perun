# Отчёт по FAIL самопроверки ПерУН: причины и правки промптов

Источник: прогон `SELF_TEST.md` в `/Users/kenny/Work/TEST-perun` → `self_test_report.md` (итог 5/6 PASS).
Единственный блокирующий FAIL — задача 5 (шаг 3, запуск xUnit через `1c_vanessa`).

## 1. Карточка FAIL

| Поле | Значение |
|---|---|
| Тест | Задача 5 «Полный цикл развёртывания и запуск xUnit-тестов», шаг 3 |
| Контракт | `1c_vanessa { action: "xunit", epf: "./build/ТестыMiniCRM.epf", ibconnection: "/F./build/ib" }` |
| Факт | exit code 1, «Ошибка чтения параметров команды» |
| Строка запуска | `vrunner xunit ./build/ТестыMiniCRM.epf --ibconnection /F./build/ib --v8version 8.3.27.1606` |
| Диагноз vrunner | Команда верхнего уровня `xunit` отсутствует; доступны `repo, run, epf, cluster, infobase, cfe, test, cf, validate` |
| Версия тулчейна | vanessa-runner 3.0.2, платформа 8.3.27.1606 |
| Шаги 1–2 (load, updatedb) | PASS, exit 0 |
| Классификация | Дефект инструментальной обвязки (не ошибка агента, не ошибка проекта) |

Обход через `additionalArgs` невозможен: подтверждено эмпирически, что дополнительные аргументы дописываются в конец строки запуска (`... --v8version 8.3.27.1606 --help`), то есть подкоманда `test` не может быть подставлена перед устаревшей `xunit`.

## 2. Корневая причина

В vanessa-runner 3.x удалена плоская команда `xunit`; запуск тестов переведён в группу `test` (`test xunit` для внешних обработок, `test yaxunit` для YAxUnit, `test vanessa` для BDD). Ветка обвязки `1c_vanessa` для действий `xunit`/`test-xunit` по-прежнему транслирует legacy-форму 2.x (`vrunner xunit <epf>`), что ломается на любой установке с vanessa-runner ≥ 3.0.

Аналогичный риск (заранее, без подтверждённого FAIL) есть у действия `run`/`run-epf`: плоская команда верхнего уровня `run` в 3.0.2 существует (`run` — запуск информационной базы), но семантика «запустить внешнюю обработку» в 3.x относится к группе `epf`, поэтому корректность действия `run` требует отдельной проверки в следующем прогоне.

## 3. Правка №1 (обязательная, блокирующая): трансляция команд `1c_vanessa`

Место: реализация инструмента `1c_vanessa` (модуль сборки аргументов vrunner).

Спецификация исправления — таблица маппинга действий в команду vrunner 3.x:

| Действие агента | Команда vrunner 3.x | Примечание |
|---|---|---|
| `init-dev`, `infobase-init` | `infobase create` | без изменений |
| `load`, `cf-load` | `cf load` | без изменений |
| `dump`, `cf-dump`, `cf-decompile` | `cf decompile` | без изменений |
| `updatedb`, `infobase-update` | `infobase update` | без изменений |
| `test`, `test-vanessa` | `test vanessa --feature-path <dir> --bddrunner-path <epf>` | без изменений |
| `xunit`, `test-xunit` | `test xunit --epf <path>` (fallback: `test yaxunit --epf <path>`) | **новая форма** |
| `run`, `run-epf` | `epf run --epf <path>` | требует подтверждения в регрессии |

Требования к реализации:

1. Не формировать подкоманду из позиционного аргумента: путь к `.epf` передавать именованным параметром (`--epf`), а не вторым словом команды.
2. Предусмотреть совместимость: перед сборкой аргументов определять мажорную версию (`vrunner --version`) и для v2.x сохранять форму `vrunner xunit <epf>`; для v3.x использовать `test xunit`.
3. При ошибке распознавания параметров vrunner (exit 1 + «Ошибка чтения параметров команды») возвращать агенту не сырой дамп справки, а структурированную диагностику: «несовместимая версия vrunner: ожидается ≥ 3.0, форма команды `test xunit`» плюс использованная строка запуска.
4. Закрыть `additionalArgs` от подмены подкоманды: сохранять инвариант «подкоманда фиксирована инструментом», а дополнительные аргументы допускать только в хвостовую часть.

Критерий приёмки правки: `1c_vanessa { action: "xunit", epf: <путь>, ibconnection: <строка> }` на vanessa-runner 3.0.2 завершается кодом 0 и возвращает отчёт раннера.

## 4. Правка №2 (агентская): маршрутизация инструментов в системном промпте

Симптом F2: при первом проходе задача 3 ушла в `1c_skill_execute` со `skill: "bsl_fix_standards"` вместо собственного инструмента, что дало «скрипт навыка не найден» и лишний шаг.

Предлагаемая вставка в блок правил о навыках (дополнить существующую таблицу маршрутизации артефактов таблицей «артефакт → инструмент»):

```
- Таблица маршрутизации инструментов (НЕ подменять инструмент навыком):
  - Проверка/исправление стандартов ИТС в .bsl/.os  -> инструмент bsl_fix_standards (НЕ 1c_skill_execute)
  - Метаданные, формы, СКД, MXL, роли, XDTO         -> 1c_skill_execute(skill: 'meta-info'|'form-info'|'skd-info'|'mxl-info'|'role-validate'|'xdto-info')
  - ИБ, загрузка/выгрузка, updatedb, BDD/xUnit      -> 1c_vanessa
  - Анализ вызовов, влияния, символов               -> 1c_call_hierarchy / 1c_impact_analysis / 1c_ast_symbols
- Категорически запрещено вызывать bsl_fix_standards через 1c_skill_execute: это самостоятельный инструмент,
  в каталоге skills он отсутствует (ошибка 'Skill script not found' = нарушение маршрутизации).
```

Также предлагается добавить в промпт диагностическую реакцию на сбои инструмента:

```
- При коде возврата != 0 внешнего раннера НЕ повторять вызов с теми же аргументами и НЕ предлагать пользователю
  интерактивный запуск 1С. Зафиксировать FAIL, привести полную строку запуска, определить, является ли
  команда устаревшей для установленной версии тулчейна, и оформить дефект обвязки.
```

## 5. Правка №3 (тестовые данные): пригодный xUnit-артефакт

2. Хранить в бенчмарке эталон ожидаемого результата (число тестов, ожидаемый exit code), чтобы PASS шага 3 подтверждался фактическим отчётом раннера, а не только кодом возврата.
3. После внесения изменений в EPF пересобирать его штатным навыком `epf-build`, а не хранить артефакт без исходной связи с `tests/`.

## 6. Правка №4 (наблюдение): область inline-LSP

Симптом F3: при `write` контрольного файла `tmp_selftest/Violation.bsl` фоновая диагностика вернула «нарушений не обнаружено», тогда как `bsl_fix_standards` по тому же файлу вернул 3 замечания (`MissingBSLDoc`, `EmptyExcept`, `QueryInLoop`).

Правки (не блокирующие):

2. Выровнять набор правил фонового анализатора с CLI-профилем, чтобы `write` не давал ложно-чистый результат относительно последующей проверки инструментом.
