# Пользовательские сценарии ИИ-помощника 1С (ПерУН)

Документ описывает работу решения со стороны конечного пользователя — разработчика 1С и главного разработчика (лида/архитектора) — в соответствии с требованиями [CASE.md](CASE.md).

---

## 1. Сценарий: Быстрый ввод в контекст («Что делает функция и переменная»)

### Проблема
Разработчик подключается к незнакомой конфигурации или модулю на несколько тысяч строк. Ручной поиск определений, цепочек вызовов и структуры промежуточных таблиц отнимает значительную часть времени.

### Роль
Разработчик 1С.

### Пользовательский путь
1. **Переключение режима:** Разработчик выбирает режим `ОБЪЯСНИТЬ` сочетанием клавиш `alt+m` или командой `/mode explain`.
2. **Запрос разработчика:**
   > «Объясни, за что отвечает процедура СформироватьДвиженияПоПартиям в модуле документа РеализацияТоваровУслуг и откуда берется локальная таблица ТаблицаСписания.»
3. **Действия помощника:**
   - Вызывает `1c_ast_symbols` для извлечения сигнатуры, директив компиляции (`&НаСервере`) и локализации границ процедуры без полного чтения файла.
   - Строит граф связей через `1c_call_hierarchy` (входящие вызовы из `ОбработкаПроведения`, исходящие вызовы в общие модули проведения).
   - Выполняет разбор SDBL-запроса, формирующего таблицу `ТаблицаСписания`.
4. **Результат для пользователя:**
   - **Назначение:** краткое описание алгоритма списания партий и расчета себестоимости.
   - **Структура переменной:** перечень колонок таблицы `ТаблицаСписания` и источники данных (табличная часть `Товары` + регистр `ОстаткиТоваровНаСкладах`).
   - **Граф вызовов:** Mermaid-диаграмма с последовательностью шагов проведения.

## 2. Сценарий: Локализация бизнес-данных («Где хранятся нужные данные»)

### Проблема
При доработке бизнес-логики разработчику требуется определить, в каких таблицах базы хранятся целевые показатели и какими документами они изменяются.

### Роль
Разработчик 1С.

### Пользовательский путь
1. **Запрос разработчика:**
   > «В каких регистрах хранятся остатки резервов товаров и какими документами формируются движения?»
2. **Действия помощника:**
   - Вызывает `1c_impact_analysis(target: "Резервы")`.
   - Сканирует метаданные 1C:EDT (`Configuration.mdo`, каталоги `AccumulationRegisters/`, `Documents/`).
   - Фильтрует документы, модифицирующие регистр в процедурах проведения (`affectsPosting = true`).
3. **Результат для пользователя:**
   - **Целевые метаданные:** регистр накопления `РезервыТоваровОрганизаций` (вид: Остатки).
   - **Состав полей:** измерения `Номенклатура`, `Склад`, `Организация`; ресурс `КоличествоРезерв`.
   - **Документы-регистраторы:** `ЗаказКлиента` (модуль объекта, строка 142), `КорректировкаРезервов` (строка 88).
   - **Навигация:** прямые ссылки на строки формирования движений.

## 3. Сценарий: Автоматическое документирование по стандарту 1С:ИТС

### Проблема
Кодовая база не содержит актуальной документации методов. Ручное оформление BSLDoc по стандартам ИТС трудоемко и часто игнорируется.

### Роль
Разработчик 1С.

### Пользовательский путь
1. **Переключение режима:** Разработчик переходит в режим `НАПИСАТЬ` (`/mode write`).
2. **Запрос разработчика:**
   > «Сгенерируй документацию для функции РассчитатьСкидкуПоАкции в общем модуле СкидкиСервер.»
3. **Действия помощника:**
   - С помощью `1c_ast_symbols` извлекает параметры, директиву выполнения и возвращаемые типы.
   - Генерирует BSLDoc строго по стандарту 1С:ИТС.
   - Применяет изменения в файл через точечный патч.
   - Фоновый LSP-клиент `bsl-analyzer` автоматически проверяет корректность добавленного блока.
4. **Результат для пользователя:**
   В коде модуля появляется стандартизированный комментарий:
   ```bsl
   // Рассчитывает итоговый процент и сумму скидки по действующим маркетинговым акциям.
   //
   // Параметры:
   //  Партнер        - СправочникСсылка.Партнеры - Получатель скидки.
   //  СуммаДокумента - Число                     - Базовая сумма до применения скидок.
   //
   // Возвращаемое значение:
   //  Структура - Ключи: "ПроцентСкидки", "СуммаСкидки".
   //
   Функция РассчитатьСкидкуПоАкции(Партнер, СуммаДокумента) Экспорт
   ```

## 4. Сценарий: Обратная связь и самокоррекция базы знаний

### Проблема
ИИ-модель может сделать неточный вывод о специфике нетиповой конфигурации. Требуется механизм обучения на замечаниях лида без дообучения внешней нейросети.

### Роль
Главный разработчик (Team Lead / Архитектор).

### Пользовательский путь
1. **Обратная связь лида:**
   > «В твоем описании ошибка: скидка по акции не применяется, если партнер оптовый. Исправь документацию функции РассчитатьСкидкуПоАкции и зафиксируй это правило для подсистемы скидок.»
2. **Действия помощника:**
   - Корректирует BSLDoc в целевой функции.
   - Записывает новое проектное правило в базу знаний репозитория (`.pi/rules/discounts.md`).
   - Добавляет правило в постоянный контекст подсистемы `Скидки`.
3. **Результат для пользователя:**
   - Обновленный diff документации в репозитории.
   - При последующих вопросах любых разработчиков о скидках помощник автоматически учитывает исключение для оптовых клиентов.

## 5. Сценарий: Безопасность данных и работа с ежедневными коммитами

### Защита конфиденциальных данных
- Помощник работает локально с файлами исходного кода 1C:EDT (`.mdo`, `.bsl`, `.xml`).
- Прямой доступ к СУБД с персональными или финансовыми данными предприятия отсутствует. В запросы к LLM попадают исключительно структуры метаданных и программный код.

### Поддержка актуальности при частых коммитах
- Индексация и навигация выполняются по рабочему дереву Git.
- При получении новых коммитов помощник анализирует актуальные файлы без необходимости пересборки базы знаний с нуля.
